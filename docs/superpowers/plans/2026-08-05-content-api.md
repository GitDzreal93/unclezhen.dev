# Content Management Public API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a secure versioned public API that lets AI agents manage products, blog posts, and projects through independently scoped bearer tokens administered from the existing admin interface.

**Architecture:** PostgreSQL stores hashed API tokens and a mutation/failed-auth audit trail. Shared server-only modules generate and verify tokens, validate resource payloads, perform content mutations, and map failures to a consistent JSON response shape. Thin Next.js route handlers authorize a resource/action scope then call those modules. An admin page creates, lists, revokes, and deletes tokens; the raw secret is returned only for the successful creation interaction.

**Tech Stack:** Next.js 15 App Router route handlers, React 19 server/client components, TypeScript, PostgreSQL via `pg`, Node.js `crypto`, existing server actions and admin-cookie authentication.

## Repository conventions to preserve

- All database changes are idempotent additions to [`scripts/setup-db.mjs`](../../scripts/setup-db.mjs), because the project applies migrations through that setup script.
- API implementation must use `query` from [`src/lib/db.ts`](../../../src/lib/db.ts), never expose database errors or token secrets, and keep all token code server-only.
- Continue using the existing `assertAdmin()` guard for token administration server actions.
- API mutations must call `revalidatePath()` for the matching public/admin routes, just as the existing admin actions do.
- Existing content schema stays single-language. This API manages the current stored content; it does not add translated database fields.

## Response and authorization contract

Every `/api/v1` response has `Cache-Control: no-store` and `X-Request-Id: <uuid>`.

```ts
type ApiSuccess<T> = { data: T; meta?: { count: number } };

type ApiError = {
  error: {
    code: "unauthorized" | "forbidden" | "not_found" | "conflict" | "validation_error" | "internal_error";
    message: string;
    requestId: string;
    details?: Record<string, string>;
  };
};
```

The six valid scopes are:

```ts
export const API_SCOPES = [
  "products:read", "products:write",
  "posts:read", "posts:write",
  "projects:read", "projects:write",
] as const;
```

`GET` requires the corresponding `:read` scope. `POST`, `PATCH`, and `DELETE` require the matching `:write` scope. Missing, malformed, expired, revoked, and unknown tokens always produce identical `401 unauthorized` responses. A valid token with an absent scope produces `403 forbidden`.

Implementation SQL shape:

```sql
CREATE TABLE IF NOT EXISTS api_tokens (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  prefix TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  scopes TEXT[] NOT NULL DEFAULT '{}',
  expires_at TIMESTAMPTZ,
  revoked_at TIMESTAMPTZ,
  last_used_at TIMESTAMPTZ,
  last_used_ip TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

```ts

  constructor(
    readonly code: "validation_error" | "not_found" | "conflict",
    message: string,
    readonly details?: Record<string, string>,

  }
}
```
